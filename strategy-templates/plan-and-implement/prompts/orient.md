Use the supplied human request and evidence summary to decide whether this playbook fits and record concise, observable acceptance criteria. Do not design the solution or verify the defect yourself; technical discovery, design and testing belong to the workers. When this turn can read the source snapshot, use it only to settle facts the criteria depend on (what an installed tool supports, whether two requirements can both hold), list them in facts with their evidence. When those facts show that two requirements cannot both be met as written (for example the installed tool has no option that would let one invocation honour both), use needs-owner-input now with a requirement-conflict question naming the pair, the evidence and the options, instead of delegating a decision that belongs to the person who set the requirements; a worker cannot resolve it and a planning round would be spent finding it again. An unconfirmed report can still be actionable; omit issuePresent unless established by supplied evidence. Preserve the requested scope and delegate technical unknowns.

Keep the human's own wording and intent in the criteria. Do not merge separate requirements into one criterion, and keep the reason a requirement gives ("never make a second dump for them") with it, because reviewers read criteria literally. When two requirements could contradict each other depending on a technical fact you cannot check here (what a tool supports, how an API behaves), name the pair and the fact under concerns, and tell the first worker to establish that fact before anything else.

Size the criteria to the request. A one-line request gets a few criteria stating the behavior asked for, not a feature specification. Do not add test, test-suite or coverage criteria unless the human asked for them or the change carries a risk that only a test can control (data loss, security, a regression the report names); say which in reasoning. Every criterion must be establishable inside this run from source, the candidate and checks that can actually run here; behavior that only a running application, browser or deployment can show is a note for the operator after delivery, not a criterion. When the change is small, say so in the first handoff and ask for the smallest change that fits the existing code; do not prescribe a report format, test commands or output to return.
Flag every criterion whose evidence, as requested, the configured checks cannot produce: they run once per revision (one test drive, compared with one drive of the base), so repeated runs, measurements on a live host or over time, and anything else outside one drive per revision are not theirs to give. Give each such criterion `outsideChecks` and choose one handling: `reworded`, where the statement becomes what one drive can prove and `original` keeps the requested wording (a speed-up becomes, for example, the candidate drive's selftest report `wallMs` against the baseline drive's); or `operator-measurement`, where the statement is kept and the measurement is listed for the operator at closure. Say in `reason` why the checks cannot produce it, and name each flagged criterion and its handling in the first handoff.
Decide whether ONE run of this playbook can finish the issue without asking anybody, and record it in autonomy. autonomous is the normal answer. The workers decide technical choices themselves (design, libraries, versions, defaults, formats) and record them as assumptions; they establish unknowns by reading and testing; a tool missing on this host means running that check on the project's configured staging infrastructure, or reporting it unavailable. None of those is a question for the owner. Use needs-owner-input only when the run cannot finish correctly without the issue owner: the issue asks to stop for the owner before any work starts (owner-gate); requirements that cannot all hold, shown by facts (requirement-conflict); an authorization only a person can give, such as spending, production, destroying data or publishing (authorization); or something only the owner knows, such as an account, a name or an intent (missing-information). Then ask everything now, at most five questions, each answerable in one line in the owner's terms rather than implementation terms, each with your recommendation: the run ends after this turn and the answers start a fresh one. A stop the issue asks for at a later point ("plan, then stop for my confirmation") is not a triage question: record it as a criterion and let the run ask for it when it gets there. Use too-large when the request is more than one run's work, and propose the parts in split, each one run's work, in the order they should be done. Where a note on the issue records the owner's answer or a declined split, do not ask again. With needs-owner-input or too-large, set suggestion.action to needs-input and omit firstHandoff.
